# Codex 100% 활용 가이드

이 문서는 현재 Codex CLI형 작업 환경을 기준으로, Codex를 가장 효율적으로 쓰는 방법을 정리한 실전 가이드다. 목표는 "좋은 질문"이 아니라 "좋은 결과"를 빠르게 얻는 것이다.

## 1. Codex가 특히 잘하는 일

- 기존 코드베이스 탐색과 구조 파악
- 버그 수정과 재현 경로 추적
- 테스트 추가, 실패 원인 분석, 회귀 방지
- 작은 기능부터 중간 규모 리팩터링까지 실제 코드 수정
- 리뷰어 관점의 코드 리뷰
- 문서 초안 작성, 정리, 자동화 스크립트 작성
- 터미널 기반 조사: 파일 검색, 설정 확인, 실행 로그 확인

반대로, 요구사항이 모호한 상태에서 "대충 예쁘게" 같은 요청은 결과 편차가 크다. 원하는 기준을 먼저 주는 편이 낫다.

## 2. 가장 중요한 원칙

Codex는 설명만 하는 것보다 직접 수정하고 검증하는 쪽에 최적화되어 있다. 그래서 아래처럼 요청해야 효율이 올라간다.

- 목적을 먼저 말한다
- 제약을 같이 준다
- 완료 기준을 적는다
- 가능하면 파일/명령/에러를 같이 준다

좋은 요청 예시:

```text
로그인 API에서 500이 나는 버그를 고쳐줘.
재현은 POST /api/login 에서 password가 비어 있을 때다.
원인은 null 처리로 보이고, 기존 응답 스키마는 유지해야 한다.
수정 후 관련 테스트도 추가해줘.
```

나쁜 요청 예시:

```text
로그인 좀 봐줘
```

## 3. 요청을 잘하는 공식

아래 4줄만 지켜도 품질이 확 올라간다.

```text
1. 목표: 무엇을 바꾸고 싶은가
2. 맥락: 어떤 파일/기능/에러인가
3. 제약: 건드리면 안 되는 것, 유지해야 할 것
4. 완료 조건: 테스트, 문서, 커밋, 성능 기준 등
```

실전 템플릿:

```text
목표: [원하는 결과]
맥락: [관련 파일, 화면, API, 에러 로그]
제약: [호환성, 스타일, 라이브러리, 일정]
완료 조건: [테스트 통과, 문서 반영, 커밋 제외 등]
```

## 4. 작업 유형별 베스트 프롬프트

### 버그 수정

```text
[증상]을 재현하고 원인까지 찾아서 수정해줘.
가능하면 최소 수정으로 처리하고, 회귀 테스트를 추가해줘.
수정 뒤 어떤 입력에서 어떻게 달라졌는지 설명해줘.
```

### 기능 추가

```text
[기능]을 현재 구조에 맞게 구현해줘.
새 의존성 추가는 피하고, 기존 패턴을 우선 따라줘.
UI/서버/테스트까지 필요한 범위만 끝까지 반영해줘.
```

### 리팩터링

```text
[대상 모듈]의 중복을 줄이되 동작은 유지해줘.
외부 API와 타입 시그니처는 바꾸지 말고, 변경 리스크가 큰 부분은 먼저 짚어줘.
리팩터링 후 테스트나 검증 방법도 같이 정리해줘.
```

### 코드 리뷰

```text
이 변경사항 리뷰해줘.
버그, 회귀 가능성, 누락된 테스트를 우선적으로 봐줘.
요약보다 finding 위주로, 심각도 순서로 정리해줘.
```

### 문서화

```text
[대상 기능]에 대한 운영 문서를 작성해줘.
개발자가 바로 따라할 수 있게 예시 명령과 주의사항을 포함해줘.
현재 코드 기준으로 사실 확인하면서 써줘.
```

## 5. Codex를 100% 활용하는 대화 방식

### 1) 한 번에 너무 많이 던지지 말고, 완료 단위를 나눈다

좋다:

```text
1단계로 원인만 찾고
2단계로 수정
3단계로 테스트 추가해줘
```

더 좋다:

```text
원인 분석부터 수정, 테스트, 결과 요약까지 한 번에 끝내줘.
단, 의존성 추가는 하지 말고 커밋은 하지 마.
```

즉, 작업 범위는 넓게 줄 수 있지만 완료 기준은 분명해야 한다.

### 2) "어떻게"보다 "무엇을 만족해야 하는지"를 준다

Codex에게 구현 디테일을 과하게 지정하면 오히려 기존 구조와 충돌할 수 있다. 아래처럼 결과 기준 중심이 낫다.

```text
SSR은 유지하고, 첫 로드 성능을 해치지 않는 선에서 검색 UI를 추가해줘.
```

### 3) 애매하면 비교 기준을 준다

```text
빠른 구현과 구조적 정리 중에서는 구조적 정리를 우선해줘.
```

```text
이번 수정은 hotfix라서 최소 변경을 우선해줘.
```

## 6. 이 환경에서 꼭 알아둘 점

### Codex는 먼저 읽고, 그 다음 수정한다

현재 환경의 Codex는 코드베이스를 먼저 탐색한 뒤 수정하는 쪽으로 설계되어 있다. 그래서 "바로 답만"보다 "파일 보고 고쳐줘"가 더 강하다.

### 기본적으로 직접 작업한다

질문이 단순한 브레인스토밍이 아닌 경우, Codex는 설명만 하지 않고 실제로 파일을 수정하고 검증하려고 한다. 즉 아래 표현이 잘 먹힌다.

```text
설명 말고 실제로 수정해줘
```

### 리뷰 요청은 일반 Q&A와 다르게 처리된다

"리뷰해줘"라고 하면 요약보다 버그/리스크/테스트 누락 중심으로 보는 경향이 있다. 리뷰를 원할 때는 이 표현이 정확하다.

```text
이 PR/변경분을 리뷰해줘. finding 위주로.
```

### 최신 정보가 필요하면 명시하는 게 좋다

버전, 가격, 정책, 외부 서비스 문서처럼 바뀔 수 있는 정보는 아래처럼 말하는 편이 안전하다.

```text
최신 기준으로 확인해줘
```

## 7. 승인과 제약을 이해하면 속도가 빨라진다

Codex는 현재 터미널과 파일 시스템 안에서 일한다. 그래서 다음을 알면 덜 막힌다.

- 로컬 파일 읽기와 수정은 잘한다
- 테스트, 빌드, 검색 같은 터미널 작업도 잘한다
- 네트워크나 샌드박스 바깥 권한이 필요한 작업은 승인 요청이 뜰 수 있다
- 위험한 명령은 자동으로 하지 않는다

실전 팁:

- 패키지 설치가 필요하면 "필요하면 승인 요청하고 진행해줘"라고 말한다
- 커밋을 원하지 않으면 미리 "커밋은 하지 마"라고 적는다
- 특정 파일만 건드리게 하려면 파일 경로를 준다

## 8. 결과 품질을 올리는 추가 지시문

아래 한 줄들이 체감 품질을 크게 올린다.

- 최소 수정으로
- 기존 스타일을 유지해서
- 테스트까지 포함해서
- 변경 이유를 짧게 설명해줘
- 성능 회귀 없게
- 접근성 고려해서
- 타입 안정성 유지해서
- 새 라이브러리 추가 없이
- 관련 문서도 같이 갱신해줘
- 내가 수정한 파일 외 다른 파일은 되도록 건드리지 마

## 9. 실전용 요청 예시 10개

### 예시 1. 에러 수정

```text
checkout 페이지에서 쿠폰 적용 시 간헐적으로 total이 NaN이 된다.
원인 재현부터 수정, 테스트 추가까지 해줘.
금액 계산 로직의 기존 public API는 바꾸지 마.
```

### 예시 2. 테스트 보강

```text
user-service 관련 테스트가 약하다.
핵심 정상 케이스와 실패 케이스를 보강해줘.
mock 남발보다는 현재 테스트 패턴을 따라줘.
```

### 예시 3. 리팩터링

```text
이 모듈의 중복된 validation 로직을 정리해줘.
동작 변경 없이 가독성과 유지보수성을 높이는 방향으로 해줘.
```

### 예시 4. 성능 개선

```text
대시보드 첫 렌더가 느리다.
병목 지점을 찾아서 가장 효과 큰 것부터 개선해줘.
측정 근거와 트레이드오프도 짧게 적어줘.
```

### 예시 5. 코드 리뷰

```text
현재 브랜치 변경사항 리뷰해줘.
사소한 스타일보다 실제 장애 가능성, 회귀, 누락된 테스트를 우선 봐줘.
```

### 예시 6. 문서 작성

```text
로컬 개발 환경 세팅 가이드를 README에 추가해줘.
신입 개발자가 그대로 따라할 수 있게 명령어 중심으로 써줘.
```

### 예시 7. 프론트엔드 UI 작업

```text
이 페이지 히어로 섹션을 더 인상적으로 개선해줘.
기존 디자인 시스템은 유지하되, 너무 평범하지 않게 해줘.
모바일 대응까지 포함해줘.
```

### 예시 8. 마이그레이션

```text
환경변수 로딩 방식을 새 설정 구조로 옮겨줘.
하위 호환은 유지하고, deprecated 경로는 주석이나 문서로 남겨줘.
```

### 예시 9. CLI 자동화

```text
배포 전에 실행할 검증 스크립트를 만들어줘.
lint, typecheck, test를 순서대로 돌리고 실패 시 즉시 종료하게 해줘.
```

### 예시 10. 빠른 조사

```text
이 저장소에서 인증 관련 진입점 파일과 토큰 검증 로직 위치만 빠르게 찾아줘.
수정은 하지 말고 경로와 역할만 요약해줘.
```

## 10. 스킬(Skill)도 활용할 것

이 환경에는 일부 작업을 위한 스킬이 따로 있다. 사용자가 이름을 직접 말하거나, 작업이 스킬 설명과 명확히 맞으면 Codex는 그 스킬 문서를 읽고 그 흐름을 따른다.

현재 확인된 예:

- `skill-creator`: 새 스킬을 만들거나 기존 스킬을 다듬을 때
- `skill-installer`: 설치 가능한 스킬 목록 확인, 스킬 설치, 외부 저장소에서 스킬 가져오기

예시:

```text
skill-creator를 써서 우리 팀용 배포 체크리스트 스킬 만들어줘.
```

```text
skill-installer로 설치 가능한 스킬 목록 보여줘.
```

## 11. 자주 발생하는 실패 패턴

- 목표 없이 구현 방식만 지시함
- 관련 에러/파일/로그를 안 줌
- "좋게 해줘"처럼 평가 기준이 없음
- 무엇을 유지해야 하는지 안 적음
- 수정만 원하면서 테스트나 검증 기준을 안 줌
- 최신 정보가 필요한데 확인 요청을 안 함

이럴 때는 결과가 틀리기보다, 결과가 애매해진다.

## 12. 가장 추천하는 실전 운영법

### 빠른 문제 해결용

```text
이 에러 고쳐줘.
원인 분석 -> 수정 -> 테스트 -> 결과 요약 순서로 끝내줘.
기존 API는 유지하고, 새 의존성은 추가하지 마.
```

### 안전한 변경용

```text
수정 전에 관련 파일과 영향 범위를 먼저 파악하고 진행해줘.
리스크 큰 부분은 보수적으로 수정하고, 검증 방법까지 포함해줘.
```

### 리뷰 품질 극대화용

```text
이 변경사항 리뷰해줘.
칭찬이나 요약보다 finding 중심으로, 심각도 순서로 정리해줘.
파일/라인 기준으로 적어줘.
```

## 13. 바로 복붙해서 쓰는 만능 템플릿

```text
[작업]
[무엇을 원하는지 한 줄]

[맥락]
관련 파일:
재현 방법:
현재 문제:

[제약]
유지해야 할 것:
건드리면 안 되는 것:
추가 라이브러리 허용 여부:

[완료 조건]
수정
테스트
짧은 결과 요약
```

## 14. 한 줄 요약

Codex를 100% 활용하는 방법은 "막연하게 시키지 말고, 목표·맥락·제약·완료조건을 명확히 준 뒤 실제 수정과 검증까지 맡기는 것"이다.
